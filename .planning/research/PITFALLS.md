# Pitfalls Research

**Domain:** Training optimization for RASHKOGIE GTA — compact tensor storage, learned embeddings, batched GPU training, CUDA mixed precision on RTX 3070 Ti (8 GB VRAM shared with GTA V)
**Researched:** 2026-05-04
**Confidence:** HIGH — derived from direct code audit of existing training scripts, preprocess_data.py, and main_model.py, plus verified PyTorch documentation

---

## Critical Pitfalls

Mistakes that cause data loss, silent wrong results, or CUDA OOM that blocks training entirely.

---

### Pitfall 1: Preprocessing Builds All Tensors in RAM Before Saving — 16+ GB Peak on 82k Records

**What goes wrong:**
`preprocess_data.py` builds Python lists (`ego_t_list`, `scene_t_list`, etc.) containing every tensor for every record, then calls `torch.cat` at the end to stack them. For 82k records at ~1 MB each of raw JSONL, the parse phase alone can consume 4–8 GB of Python heap due to JSON object overhead (~49 bytes per string key, 28 bytes per Python float). The list of `[1, 46]` tensors for ego_t across 82k records is another ~19 MB; but `entities_t` at `[1, 32, 24]` per record adds ~600 MB of tensor objects. Total intermediate peak before `torch.cat`: 6–10 GB RAM simultaneously in Python. On a system running GTA V and a browser, this will trigger paging or OOM kill.

**Why it happens:**
The current implementation appends individual `[1, dim]` tensors to lists instead of pre-allocating a `[N, dim]` output buffer and writing records into it. This is natural when N is unknown at start, but it doubles peak memory: both the list of tensors and the final stacked tensor exist simultaneously during `torch.cat`.

**How to avoid:**
Two-pass approach: first scan all JSONL files to count valid records (cheap, just count non-comment non-empty lines), then pre-allocate `torch.zeros(N, 46)` output tensors for each field, then fill row-by-row in a second pass. This eliminates the intermediate list entirely. Peak RAM drops to approximately the output tensor size (~800 MB) plus one record's Python objects at a time. Alternatively, process and save one session file at a time as a partial `.pt`, then merge at the end.

**Warning signs:**
- Windows Task Manager shows Python process RAM climbing past 8 GB during preprocessing
- Process is killed silently (no exception, just disappears)
- `session_20260503_013325.jsonl` alone is 25 GB — parsing it into Python dicts will use 25–50 GB before any tensor creation

**Phase to address:** Phase 1 (Data Format) — the preprocessing tool must use pre-allocation or per-session chunking before processing any data.

### Pitfall 2: Existing `.pt` Format Stores Categorical Fields as float32 — Adding Embeddings Requires Long and Breaks Backward Compatibility

**What goes wrong:**
`preprocess_data.py` calls `build_state_tensors()` which stores `type_id` and `bucket_id` (entity categorical fields) as `float32` inside `entities_t` at indices 0 and 1. The intuition is that they are "just numbers." Adding `nn.Embedding` layers requires these fields to be `torch.long` indices. When the new encoder tries to call `embed_type(entities_t[:, :, 0].long())`, it works, but silently truncates float values (e.g., `type_id = 3.9` becomes 3, `type_id = -0.5` becomes 0). More critically: any `.pt` file generated by the current preprocessing must be regenerated — old checkpoints and preprocessed files are incompatible with the new encoder.

**Why it happens:**
`build_state_tensors()` uses `dtype=torch.float32` for the entire entities tensor including categorical columns. There is no distinction in the tensor format between continuous and categorical fields. This is sufficient for float-based encoding but incorrect for embedding lookups.

**How to avoid:**
Change the preprocessed format before processing 88 GB of data. Either: (a) split the entities tensor into `entities_continuous` (`float32`, all non-categorical fields) and `entities_categorical` (`torch.long`, just `type_id` and `bucket_id`), or (b) store a separate `entity_cats` tensor of shape `[N, 32, 2]` as `torch.long` alongside the existing `entities_t` as `float32` with those positions zeroed out. Option (a) is cleaner. Any existing `.pt` preprocessed file from the old format must be deleted and regenerated — do not attempt `load_state_dict` with mismatched field layouts. Add a `format_version` key to saved `.pt` files so training scripts can detect stale format at load time.

**Warning signs:**
- Existing `preprocessed.pt` loads without error but embedding forward pass produces wrong results (all embeddings come from index 0)
- `entities_t[:, :, 0].long()` produces values like 32768 or -1 because float values outside `[0, num_categories)` get silently truncated to invalid indices
- `IndexError: index out of range in self` at training startup when a float-as-long value exceeds `num_embeddings`

**Phase to address:** Phase 1 (Data Format) and Phase 2 (Embeddings) — must be coordinated. Define the new tensor format in Phase 1 before generating any data. Phase 2 embeds into a format that was designed for it.

### Pitfall 3: `encoder_weights` Is a Plain Dict, Not an `nn.Module` — AMP and Optimizer Registration Require Manual Handling

**What goes wrong:**
The encoder is implemented as a dict of `nn.Module` instances (`weights["ego_mlp"]`, `weights["scene_mlp"]`, etc.) rather than a subclassed `nn.Module`. This pattern works for forward passes but creates three concrete problems when adding AMP and batched training:

1. **GradScaler parameter collection:** `scaler.step(optimizer)` unscales gradients for all optimizer parameter groups. The optimizer is built by manually listing parameters from the dict. If any new sub-module (e.g., embedding tables) is added to the dict but not explicitly added to the optimizer's parameter list, those parameters receive no gradient updates — silently.

2. **`torch.amp.autocast` context:** `autocast` casts ops based on the input tensor dtype. Because the encoder is not an `nn.Module`, calling `model.half()` or `model.to(memory_format=...)` does not work on it. All modules must be moved individually using the existing `to_device()` utility, and the same must be done for any new embedding modules added to the dict.

3. **`freeze_module` misses new entries:** `training_utils.freeze_module()` iterates over dict values and calls `requires_grad_(False)` on anything with `.parameters()`. If embedding modules are added as new keys after the freeze call (e.g., in a resume path), they will remain trainable during a phase that expects them frozen.

**How to avoid:**
For this milestone, keep the dict pattern but enforce two rules: (a) maintain an explicit `all_params` list that is rebuilt whenever a new sub-module is added to the dict, and (b) add an assertion at training start that `set(id(p) for p in optimizer.param_groups[0]['params']) == set(id(p) for all modules in encoder_weights)`. For Phase 3 (Batching) consider converting `encoder_weights` to a proper `nn.Module` subclass — this eliminates all three issues and enables `model.eval()`, `model.train()`, and `torch.compile()`.

**Warning signs:**
- Embedding lookup tables are in the encoder dict but embedding loss is not decreasing (parameters not in optimizer)
- `torch.cuda.amp.GradScaler` reports skipping steps even at low learning rate (embedding parameters receiving `inf` gradients because they were not added to the scaler's parameter list)
- After resuming from checkpoint and calling `freeze_module(encoder_weights)`, embeddings are still trainable

**Phase to address:** Phase 2 (Embeddings) — add embeddings explicitly to optimizer param list and verify with assertion. Phase 3 (Batching/AMP) — consider `nn.Module` refactor.

### Pitfall 4: Per-Record Python Loop Inside Batch — GPU Sits Idle 90% of the Time

**What goes wrong:**
`main_model/train.py` processes a batch with:
```python
for idx in batch_indices:
    tensors_t = {k: pt_data[k][idx].unsqueeze(0).to(device) for k in ...}
    z_t = encode_tensors(tensors_t, encoder_weights)
    ...
    loss = mse_loss(z_next_pred, z_t1_real)
    total_loss = total_loss + loss
```
Each call to `encode_tensors()` is a separate GPU kernel launch for a `[1, dim]` tensor. PyTorch GPU kernels have a fixed launch overhead (~5–15 µs); for a batch of 32, this means 32 separate ego_mlp forward passes, 32 separate attention computations. With 236k records and a 32-sample batch, that is ~7,400 GPU launches per epoch where a fully vectorized batch would use ~7,400/32 = ~230 launches. The GPU is never fully utilized. Profiling on small models like this encoder shows 10–50x speedup when using true batch dimensions.

**Why it happens:**
The original code was written for online inference (`encode_state` takes a single raw dict). Training was added by iterating over records and accumulating scalar losses. Vectorizing requires changing the encoder API to accept `[B, dim]` instead of `[1, dim]` and ensuring all intermediate shapes change accordingly.

**How to avoid:**
Change `encode_tensors()` (and all callers in training) to accept a pre-stacked batch: `ego [B, 46]`, `scene [B, 16]`, `route [B, 14]`, `entities [B, 32, 24]`, `mask [B, 32]`. All existing MLP layers (`nn.Linear`) already support batch dimensions transparently. The attention mechanism (`multi_head_attention`) must be verified to handle `[B, ...]` query shapes. The training loop then becomes: `z_t = encode_tensors(batch_tensors, weights)` — one GPU call for the entire batch. Do not change the inference path (`encode_state` for live GTA play) — keep it `[1, dim]` to avoid breaking the online pipeline.

**Warning signs:**
- `nvidia-smi` shows GPU utilization at 10–20% during training
- `torch.cuda.utilization()` metric stays below 30%
- Training throughput (records/sec) does not scale when batch_size is doubled

**Phase to address:** Phase 3 (Batching) — this is the core deliverable of that phase.

### Pitfall 5: Mixed Precision OOM From Activations, Not Weights — On 8 GB VRAM With GTA Running

**What goes wrong:**
On an RTX 3070 Ti with 8 GB VRAM, GTA V in the background holds 2–4 GB of VRAM for textures and frame buffers (varies by settings). Available for PyTorch: ~4–6 GB. Mixed precision (fp16) reduces weight memory by 2x but does NOT reduce activation memory by 2x in all cases — intermediate activations in `autocast` regions are stored in fp16, but the attention score matrices `[B, 32, 32]` can still be large. More importantly, GradScaler stores the scaled fp32 master copy of the optimizer state (Adam stores first and second moment in fp32 regardless of AMP), which uses the same memory as full fp32 training. OOM can appear only during the backward pass when both the fp16 activations and the fp32 gradient accumulation buffers coexist.

**Why it happens:**
AMP reduces weight storage and most activation storage, but Adam optimizer state (2 fp32 tensors per parameter) is always fp32. For a 3-layer MLP with hidden_dim=128, the savings are modest. The real OOM risk is: batch_size × seq_len × attention complexity. With `[B, 32, 32]` attention at batch=128, the attention weights alone are 128×32×32×2 bytes (fp16) = 8 MB — fine. But if GTA is using 4 GB and training peaks at 3.5 GB during backward, a 7.5 GB peak on an 8 GB card will OOM.

**How to avoid:**
Reserve 3 GB for GTA (GTA's texture budget changes dynamically). Set `batch_size` so that peak training VRAM stays under 4 GB. Profile with `torch.cuda.max_memory_allocated()` after the first backward pass with the intended batch size. Use `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True` to reduce fragmentation from the allocator's block splitting. Call `torch.cuda.empty_cache()` once before each training session (after GTA session, before training). Start with `batch_size=32` and increase only if the first epoch completes without OOM. Do not start with `batch_size=256` "to utilize GPU fully" — profile first.

**Warning signs:**
- `RuntimeError: CUDA out of memory` appearing only during `.backward()`, not during forward
- `nvidia-smi` shows VRAM at 7.8/8.0 GB right before crash
- OOM is intermittent (GTA VRAM usage fluctuates with scene complexity)

**Phase to address:** Phase 4 (Mixed Precision) — set conservative default batch size, document the GTA headroom requirement, add memory profiling assertion at training start.

### Pitfall 6: GradScaler Skips Steps Silently — Model Does Not Update for Entire Epochs

**What goes wrong:**
`GradScaler` works by scaling the loss before backward, then checking gradients for `inf`/`NaN` before calling `optimizer.step()`. If gradients contain `inf`/`NaN`, the optimizer step is skipped and the scale factor is halved. During the first few batches of training with a high learning rate or poorly initialized embeddings, gradients can be consistently `inf` — causing GradScaler to skip EVERY step and halve the scale on each batch until the scale reaches a floor. The model never updates. Training loss appears constant. The developer sees no error.

**Why it happens:**
New `nn.Embedding` layers added to the encoder are initialized with `torch.randn` by default (std=1.0). With a high initial learning rate (e.g., `1e-3`) and a large vocab size (874 tokens), the embedding gradient for a frequently-used token can be very large on the first backward pass. In fp16, large gradients overflow to `inf` immediately. GradScaler detects this and skips. Scale halves. Next step: same issue. The scale reaches ~1.0 (floor) and every step is skipped.

**How to avoid:**
After adding `GradScaler`, add a monitor block to count skipped steps:
```python
scale_before = scaler.get_scale()
scaler.step(optimizer)
scaler.update()
scale_after = scaler.get_scale()
if scale_after < scale_before:
    logging.warning("GradScaler reduced scale to %.0f — possible inf/NaN in grads", scale_after)
```
Initialize embedding weights with smaller std: `nn.init.normal_(embed.weight, std=0.01)`. Start with `lr=1e-4` for the first embedding training run. If skipping persists for more than 5 consecutive steps, disable AMP for that run and debug the gradient source.

**Warning signs:**
- Training loss is exactly constant for many steps
- `scaler.get_scale()` decreasing rapidly (from 65536 to 1 in 16 steps means 16 consecutive skip events)
- No exception, no `NaN` in logged loss — the loss never gets written because optimizer.step is skipped

**Phase to address:** Phase 4 (Mixed Precision) — add the scale monitor from the start.

### Pitfall 7: OneDrive Sync Corrupts `.pt` Files During Write on Windows

**What goes wrong:**
The project directory is at `C:\Users\laksh\OneDrive\Documents\rash_kog`. Windows OneDrive background sync can open a file handle on `.pt` or `.jsonl` files during or immediately after a write. `torch.save()` uses Python's `pickle` to write to the file object; if OneDrive acquires a read lock during the write, the resulting `.pt` file is truncated or corrupted. The corruption is silent — `torch.save()` completes without error, but the file is half-written. `torch.load()` on the next training run raises `pickle.UnpicklingError` or `EOFError`.

**Why it happens:**
OneDrive uses a file system filter driver that intercepts file close events and immediately begins uploading. For files larger than ~100 MB (the preprocessed `.pt` files will be ~800 MB), the upload takes long enough that the next process opening the file can conflict.

**How to avoid:**
Write large `.pt` files to a non-OneDrive temp directory first, then move them atomically:
```python
import tempfile, shutil
tmp = Path(tempfile.mkdtemp()) / "preprocessed.pt"
torch.save(data, tmp)
shutil.move(str(tmp), str(output_path))
```
Alternatively, pause OneDrive sync during preprocessing (right-click → Pause syncing). Add a post-save verification: immediately reload the written file and compare `data['ego_t'].shape` to the expected shape. For checkpoint files, use a `.tmp` suffix during write then rename on success:
```python
torch.save(checkpoint, str(path) + ".tmp")
Path(str(path) + ".tmp").rename(path)
```

**Warning signs:**
- `EOFError` or `UnpicklingError` when loading a recently saved `.pt` file
- `.pt` file size is not a round multiple of 4 bytes (truncated mid-tensor)
- Issue appears only after a period of not running Python (OneDrive had time to intervene)

**Phase to address:** Phase 1 (Data Format) — establish the write-to-temp-then-rename pattern before creating any large `.pt` files.

## Technical Debt Patterns

Shortcuts that seem reasonable but create long-term problems specific to this milestone.

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Keep encoder_weights as plain dict | No refactor needed, existing code unchanged | AMP parameter tracking must be done manually; cannot use `model.train()`/`model.eval()`; `torch.compile()` cannot trace it | Acceptable for Phase 2–3 if explicit param list assertions are added; migrate to nn.Module before Phase 4 if possible |
| Use `.long()` cast at runtime instead of storing long tensors in `.pt` | No format change to existing code | Silently truncates floats that were stored as categoricals; loses value if float has decimal component | Never acceptable for new format; only tolerable as temporary shim during migration |
| Skip GradScaler, use fp16 weights manually | Simpler code | Manual fp16 has no dynamic loss scaling; will get inf/NaN on first training step with small batches | Never acceptable for training stability |
| Process one JSONL session at a time then concatenate | Avoids 16 GB RAM peak | Multiple passes over large files; intermediate `.pt` files to manage | Acceptable and recommended for Phase 1 |
| batch_size=1 with AMP enabled | Easiest to validate AMP is working | No speed benefit from GPU batching; attention overhead per-call is larger than the compute | Only acceptable as a smoke test, not for real training |
| Store entities as float32 with categoricals at index 0–1 | No change to build_state_tensors | Must `.long()` cast at every forward pass; float precision errors can corrupt index if value is e.g. 3.9999 | Never acceptable after embedding integration |

## Integration Gotchas

Common mistakes when connecting the new features to the existing pipeline.

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| Embedding layer + frozen encoder | Adding embedding to encoder dict but not adding it to the `all_params` list passed to the optimizer — embedding never trains | Rebuild `all_params` after any module is added to the encoder dict; add assertion that `len(all_params) == sum(p.numel() for p in all_params)` matches expected param count |
| AMP + custom attention (`multi_head_attention.py`) | Wrapping the attention forward call in `autocast` without verifying it returns fp16 — subsequent ops get dtype mismatch errors | Verify `attn_output.dtype == torch.float16` after the first autocast forward pass; add `logging.debug("attn dtype: %s", attn_output.dtype)` |
| AMP + MSE loss between z_next_pred and z_t1_real | Both are fp16 inside autocast; MSE of fp16 values can underflow for small prediction errors (< 6e-5) giving zero loss | Cast loss inputs to fp32 before computing MSE: `mse_loss(z_next_pred.float(), z_t1_real.float())` |
| Batched encode_tensors + per-record reward head | Batching the encoder produces `z_t [B, 128]` but reward head expects `z_parent [1, 128]` — shape mismatch on first training step | Vectorize reward head training in the same phase as encoder batching; do not mix batched encoder with per-record reward head calls |
| New `.pt` format + existing `StreamingJSONLDataset` fallback | Old JSONL dataset is still the fallback if `preprocessed.pt` does not exist; JSONL records still contain float categoricals with no `long()` conversion | The JSONL fallback path in all train.py files must also apply the categorical extraction and `long()` conversion when embeddings are active |
| GradScaler + encoder_weights dict optimizer | `scaler.step(optimizer)` checks grads for params in optimizer's param groups; if embedding module was added to `encoder_weights` dict but not to optimizer, GradScaler step will succeed but that module won't update | Always call `optimizer = Adam(all_params, ...)` after any dict mutation, or maintain a consistent `all_params` reference |

## Performance Traps

Patterns that produce correct results but poor GPU utilization.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| `unsqueeze(0).to(device)` inside the batch loop | Each record does a separate H2D transfer; PCIe bandwidth is saturated by many small copies | Pre-load entire batch from `pt_data[key][batch_indices]` as a slice (no loop), then do one `.to(device)` call for the whole batch | Immediately — any batch size > 1 |
| `torch.cat` on a Python list of per-record tensors to build a batch | Creates N tensors then concatenates them; 2× peak memory and N kernel launches | Pre-slice from pre-loaded `.pt`: `pt_data['ego_t'][batch_indices]` gives `[B, 46]` directly | Any batch_size; worse as batch grows |
| `total_loss = total_loss + loss` accumulation across Python for-loop | Builds a Python-level computation graph of N scalar additions; N backward calls accumulate separately | Stack batch outputs, compute loss on stacked tensors, single backward | Breaks GPU utilization above batch_size=16 |
| `torch.cuda.empty_cache()` inside the training loop per-batch | `empty_cache()` is slow (~10 ms) and does not free live tensors; calling it per-batch adds 10 ms × N_batches overhead per epoch | Call `empty_cache()` only once at session start, never inside the training loop | Immediately for large datasets |
| Enabling AMP but keeping batch_size=1 | AMP reduces memory; batch_size=1 leaves GPU at <5% utilization; no speedup | After enabling AMP, verify `nvidia-smi` GPU utilization is >50% — if not, increase batch_size | Small batch always; AMP doesn't help small batches |
| Pre-loading entire `preprocessed.pt` to GPU (`pt_data.to('cuda')`) | For 236k records, the tensor file is ~800 MB; loading to GPU consumes all remaining VRAM before training starts | Keep `pt_data` on CPU; slice and transfer per batch | Immediately on 8 GB VRAM shared with GTA |

## "Looks Done But Isn't" Checklist

Things that appear complete but are missing critical pieces specific to this milestone.

- [ ] **Preprocessing complete:** Verify that `preprocessed.pt` contains a `format_version` key and that the categorical fields (`entities_cat`) are `torch.long` dtype — not just that the file was written without error.
- [ ] **Embedding integration:** Verify that embedding lookup tables are in the optimizer's param groups by checking `sum(p.numel() for g in optimizer.param_groups for p in g['params'])` equals expected total parameter count including embeddings.
- [ ] **Batched encoder:** Verify that `encode_tensors` accepts `[B, dim]` inputs by running it with `B=32` and checking output shape is `[B, 128]` — not just that it works with `B=1`.
- [ ] **AMP enabled:** Verify AMP is actually casting ops to fp16 by checking `z_t.dtype` inside the autocast block — training can appear to work without autocast if the context manager is applied incorrectly.
- [ ] **GradScaler active:** Add a one-time log of `scaler.get_scale()` on step 1 to confirm it is not 1.0 (which would mean scaling is not working).
- [ ] **GTA VRAM headroom:** Before each training run, log `torch.cuda.memory_allocated()` and `torch.cuda.memory_reserved()` after the first forward pass to confirm peak stays under 5 GB.
- [ ] **Capture pipeline updated:** `capture_states.py` still writes raw JSONL — confirm the new inline tensor format has been implemented and verify the output file size is ~3.4 KB/record (not ~1 MB/record).
- [ ] **Old preprocessed.pt deleted:** If any module's `training_data/` directory contains a `preprocessed.pt` created with the old float-only format, it must be deleted before training with embeddings — it will be loaded silently by the fallback path.

## Recovery Strategies

When pitfalls occur despite prevention.

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Preprocessed .pt built with float categoricals | MEDIUM | Delete `preprocessed.pt`, regenerate with new format script; takes hours on 88 GB but is fully automated |
| OneDrive-corrupted .pt file | LOW | Delete corrupted file, rerun preprocessing; add write-to-temp-then-rename going forward |
| GradScaler stuck skipping every step | LOW | Disable AMP temporarily (`with torch.amp.autocast('cuda', enabled=False):`), train one epoch to stabilize weights, re-enable AMP with lower `lr` and smaller embedding init std |
| OOM during training backward pass | LOW | Halve batch_size; if still OOM, train GTA at lower graphics settings to free VRAM, then retry |
| Embedding not in optimizer (no gradient) | MEDIUM | Rebuild optimizer with explicit param list; may need to restart training from last checkpoint |
| Encoder dict → nn.Module refactor breaks checkpoints | HIGH | Use `strict=False` in `load_state_dict` with manual key remapping; document mapping in code comments |
| Float categoricals silently indexed to wrong embeddings | HIGH | Detected only by comparing validation MSE before/after embedding fix; requires reprocessing all data and retraining encoder from last good checkpoint |
